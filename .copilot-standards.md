# Project Coding Standards

## Architecture & Structure
- Features are organized in: `Features/SoapApplications/` and `Features/Dashboard/`
- Each feature follows: `[FeatureName]/Pages/`, `[FeatureName]/Components/`, `[FeatureName]/Services/`

## Blazor Development
- **ALWAYS** use code-behind files (`.razor.cs`) instead of `@code` blocks
- Pattern: `Page.razor` + `Page.razor.cs` + `Page.razor.css`
- Code-behind class must be `public partial class PageName : ComponentBase`

## CSS Standards
- Define default values as CSS variables: `--variable-name: value;`
- Use variables in custom styles: `property: var(--variable-name);`
- Keep variables in: `wwwroot/css/variables.css`

## C# Coding Standards
- Use PascalCase for public properties and methods
- Use camelCase for private fields (prefixed with `_`)
- Async methods should have `Async` suffix
- Use `// <summary>` XML comments for public APIs
- Maximum line length: 120 characters

## Execution & Scope Rules
- **Zero Unrequested Edits:** Modify ONLY the lines, functions, or files required to fulfill the user's explicit request. Do NOT refactor, reformat, or clean up surrounding code.
- **Dependency Awareness:** Always refer to the relevant `.csproj` file before introducing or updating NuGet packages in a project.
- **Solution Safety:** Do not alter project references in `ServiceHubEnterprise.slnx` unless explicitly instructed.
- **Out-of-Scope Changes:** If a task requires modifying files outside the requested context, stop and ask for permission before generating code.

## Business Spec — Mock Database (mock_db) Configuration

The solution uses a central `mock_db/` folder at the solution root for all mock/seed data (JSON files, WSDL content, templates).

**Folder Layout:** mock data is grouped by feature domain — `Soap/` (apps/executions/test-cases/templates-page), `Soap/Request/` (request files + request executions), `Wsdl/` (records/versions/templates/sync-history/content-map + `*.wsdl`), `Rest/` (apps/request files), `Dashboard/` (health/metrics/users/activity/uptime). File names passed to `MockDbLoader.LoadJsonAsync`/`SaveJsonAsync` include the subfolder prefix (e.g. `"Soap/soap-apps.json"`, `"Wsdl/wsdl-records.json"`, `"Soap/Request/request-files.json"`).

**Configuration Rules:**
- The path to `mock_db/` is configured via `MockDb:Path` in the WebApp's `appsettings.json`.
- The path is resolved by `MockDbLoader` (in `Features/ServiceHubEnterprise.SoapApplications/Services/`) using `IConfiguration` exclusively — no fallback logic.
- If `MockDb:Path` is missing or empty, `MockDbLoader` throws `InvalidOperationException`.
- If the resolved directory does not exist, `MockDbLoader` throws `DirectoryNotFoundException`.
- `MockDbLoader` is registered as a singleton via DI in `ServiceHubEnterprise.SoapApplications/DependencyInjection.cs`.

**Usage:**
- Consumed by `SoapAppStore`, `WsdlSyncStore`, and Razor pages (`RequestFiles.razor`, `Templates.razor`, `WsdlSync.razor`).
- The path is relative to `Directory.GetCurrentDirectory()` (i.e., the WebApp's working directory). Currently set to `"../../mock_db"`.

## SOAP Execute & Test Cases — Feature Map (2026-08-02)

The SOAP feature now has a simulated execution engine and test-case system. New/moved pieces:

- **Execution engine**: `IExecutionEngine` + `SimulatedSoapExecutionEngine` in `Services/Execution/`. Deterministic staged pipeline (`ExecutionStage` enum), generates request/response XML, parses embedded base64 fields (with decoded preview) into `ParsedFields`, simulates failures when the file name/operation contains `"fail"`/`"error"`, and blocks files of disabled apps.
- **Execution data**: `mock_db/Soap/soap-executions.json` (group-based). Models: `SoapExecutionGroup` → `SoapExecutionFile` → `SoapExecutionLog` / `SoapParsedField` / `SoapExtractionResult`. `SoapExecutionStore` persists via `MockDbLoader.SaveJsonAsync`.
- **Test cases**: `mock_db/Soap/soap-test-cases.json`; `SoapTestCaseStore`; models `SoapTestCase` + `SoapExtractor` (type `xpath`/`jsonpath`/`pdf`, source `request`/`response`, optional `ExpectedValue`). Created from the Request Files page ("Test Cases" row action); run at the `RunningTestCases` stage; results shown in the Execute & History "Test Extractions" tab.
- **`SoapRequestFile`** now has optional `Content` + `TestCaseIds`. The Request Files page uses this shared model (no local record).
- **Routes**: `/soap/execute-history` (rebuilt — group history grid + `ExecutionFileDetails` component with Request/Response/Parsed/Extractions/Logs tabs). Supports `?file=`, `?app=`, `?group=` query entry points (per-file history + group pre-selection).
- **Config**: `MockDb:ExecutionStageDelayMs` (default 500; tests set 0).

## Implementation Gotchas (SOAP Execute / Test Cases)

- **Razor lambdas + string literals**: `@onclick="() => x = "str""` breaks the Razor tokenizer (error CS1525). Use a loop over `(string Key, string Label)[]` with a captured local and a `SetActiveTab(tab.Key)` handler instead.
- **bUnit does not reliably await async event handlers** that use `Task.Delay` + `Progress<T>` (a click-driven execute test was flaky; the group persisted in "running" state). For page wiring tests, inject a synchronous stub `IExecutionEngine`; test the real engine separately.
- **Don't assert on `mock_db` JSON files right after an async UI action** — `File.WriteAllTextAsync` is not atomic (torn reads). Assert on the singleton store's in-memory collection instead.
- **XPath over namespaced XML**: `doc.XPathEvaluate("//status")` returns `IEnumerable<object>` of `XElement`s — convert each via `XElement el => el.Value` (NOT `ToString()`, which yields markup). Unprefixed XPath doesn't match default-namespace elements; the engine falls back to a `local-name()` rewrite.
- **Progress callback**: use `_ = InvokeAsync(StateHasChanged);` (dispatcher-safe) rather than calling `StateHasChanged()` directly.
- **New page services break existing bUnit tests**: when a page gains `@inject`/`[Inject]` dependencies (e.g., `SoapExecutionStore`, `SoapTestCaseStore`, `WsdlSyncStore`, `IExecutionEngine`), update that page's test `Setup` to register them.
- **App delete cascades**: removing an app deletes its request files (persisted), test cases (persisted) and WSDL records+versions (in-memory); execution history is intentionally kept.
